Achievements must stay one control per bullet — this is a correctness constraint, not a style choice

CLAUDE.md: achievement ↔ editor-text conversion lives only in Core/Models/AchievementLines, and JobTailoringService addresses achievements by index through it. A single multi-line textarea would make the index depend on how the user happened to wrap their text, and accepted AI rewrites would land on the wrong bullet.

So each bullet is its own bound control with a stable index. That is also what makes the per-bullet Rewrite affordance possible — the AI acts on one addressable line rather than reflowing the block. Anything that reintroduces free-text splitting in the UI layer breaks tailoring silently.

Resolves: two-column grid or one?

Both, by field length. Title, company, location and dates are short and benefit from pairing; description and achievements span the full width. A blanket single column wastes horizontal space on a flexible layout, and a blanket two-column squeezes multi-line text into half-width boxes.

Only one entry is expanded at a time. Three roles with three achievements each is ~30 controls; collapsed summary rows keep the section navigable and make drag-reordering practical. The summary line carries what identifies the entry — title, company, dates, and an achievement count so nothing feels hidden.

"Current" is a checkbox that disables the end date, not a magic empty value. Dates render through ResumeDateFormat/DateRange under invariant culture; the UI should never let a user type something the formatter has to guess at.
