# ResumeBuilder review and adoption plan

ResumeBuilder has enough features to be useful today. Its strongest proposition is a free desktop app that needs no account, keeps documents locally, and supports optional local AI. Growing adoption now depends on making that promise dependable: imports must preserve content, job variants must preserve the base, exports must match the preview, and application records must preserve what was sent.

The review found **20 defects: 18 reproduced with isolated checks and two traced through the code**. Prioritize the content, credential, and persistence defects before a broad promotion campaign. Follow with recovery, a faster first session, and a small user feedback programme. A hosted rewrite and additional templates have lower priority.

The business objective, confirmed for this review, is **growing adoption of the free open-source app**.

## Scope and validation

Baseline: commit `524fbee` on `main`, version `1.2.3`. Reviewed the App commands and XAML, domain services, repositories and schema upgrades, sync, import and export paths, template infrastructure, CI and packaging, privacy copy, existing designs, and roadmaps. No production source or UI was changed.

| Check | Result |
| --- | --- |
| `dotnet test ResumeBuilder.sln` | 430 passed, 3 skipped, 0 failed. The skipped tests call the live Anthropic API. |
| `dotnet build ResumeBuilder.sln --configuration Release -warnaserror` | 0 warnings, 0 errors. |
| `dotnet list ResumeBuilder.sln package --vulnerable --include-transitive --format json` | No vulnerable packages reported by the configured feed at review time. |
| Isolated diagnostic checks | 18 defects reproduced using synthetic resumes, temporary databases and folders, and a synthetic API key. |

| Platform coverage | Execution on Windows. macOS and Linux installation, accessibility, and installed auto-update behaviour require separate validation. |

The diagnostic project is outside the solution and does not run in CI:

```powershell
dotnet run --project docs/reviews/probe/ReviewProbe.csproj --configuration Release
```

It reports whether baseline defects are reproducible, so `CONFIRMED` means a bug exists. It is not a passing regression suite. During repairs, replace these demonstrations with tests asserting the corrected behaviour. The probe uses reflection to reach App commands without starting the desktop UI. Its delayed repository deliberately exposes an asynchronous save boundary. It writes synthetic data under a new temporary directory, which it prints, and does not open the user's resume database or send AI requests.

See [the captured results](probe-results-2026-10-15.txt) and [the probe source](probe/Program.cs).

## Defects and proposed fixes

P1 means repair before promoting the affected workflow. P2 means a broken capability or misleading result that belongs in the next repair cycle. These priorities reflect impact; they are not estimates of implementation difficulty.

### B01 Native backup import discards document content

**P1. Reproduced.** [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs#L2995), `ImportJsonResumeAsync`.

The UI sends every selected JSON file to the `JSON Resume` importer. The content-sniffing `JSON` importer already exists, but the UI bypasses it. Exporting Jane Doe through `JSON (App Backup)` and importing through the UI route returned success with an empty name and zero experiences. The control using `JSON` preserved Jane.

**Fix:** route the JSON picker through `JSON`, and describe both supported formats in its label. Retain the specialized importer for explicitly typed API callers. Reject unrelated JSON rather than accepting an empty document.

**Acceptance:** export a fully populated native backup, import through the same command used by onboarding and the menu, and compare all content, visibility, order, and styling. Repeat with standard JSON Resume.

### B02 Plain text export has the wrong format identifier

**P2. Reproduced.** [MainWindow.axaml](../../src/ResumeBuilder.App/ResumeBuilder.App/Views/MainWindow.axaml#L220), export flyout; [TextExporter.cs](../../src/ResumeBuilder.Export/ResumeBuilder.Export/TextExporter.cs#L12).

The toolbar sends `TXT`; the registered exporter uses `TEXT`. Selecting Plain text produces an unknown-format error even though tests calling `TEXT` pass.

**Fix:** use `TEXT` consistently. Introduce shared format identifiers or build choices from registered exporters to prevent string mismatches.

**Acceptance:** every visible export action resolves to a registered exporter and writes a readable file.

### B03 Changing the AI endpoint retains the previous bearer credential

**P1. Reproduced without sending requests.** [LocalAiService.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/SmartContent/LocalAiService.cs#L39), `Configure` and `ConfigureLocal`.

`Configure` adds authorization to the shared HttpClient defaults. `ConfigureLocal` changes the endpoint and marks the service configured, but leaves that header intact. After configuring a synthetic cloud key and switching to localhost, the previous bearer header remained. The UI clears its key field, which makes the retained transport credential particularly unexpected.

**Fix:** attach authorization to individual requests from an immutable endpoint and credential configuration. Clear credentials when switching to a keyless local endpoint. Validate HTTP/HTTPS schemes and require HTTPS for remote endpoints. Apply settings atomically so a failed validation cannot change the active provider behind an unchanged privacy notice.

**Acceptance:** capture requests against loopback test servers. Switching endpoint or provider never forwards the previous endpoint's key; choosing a local endpoint emits no prior cloud credential. No real key is needed for these tests.

### B04 Applications do not preserve the resume that was sent

**P1. Reproduced.** [JobApplication.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/Models/JobApplication.cs), [MainWindowViewModel.Applications.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.Applications.cs#L96).

An application stores a mutable `ResumeId`, with no revision or exported document snapshot. Track a resume, edit and save it, then reopen it from the application: the later content appears. Deleting the resume makes the original content unavailable. This contradicts the README's promise of reopening the exact version the company read. Tracking also does not save dirty existing resumes, and continues after a failed first save.

**Fix:** introduce an immutable resume revision referenced by the application. Capture the content and template settings that were sent. Associate an exported PDF and export timestamp when available. Allow draft applications to link to editable resumes, and create the sent revision on marking an application Applied. Stop tracking if the required save fails.

**Acceptance:** editing or deleting the source leaves the sent revision available. Two applications can reference different revisions of one resume. Existing records migrate as live links with unknown historical content; do not label a newly captured revision as historical truth.

### B05 Application edits rewrite dates

**P2. Reproduced.** [ItemViewModels.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/ItemViewModels.cs#L787), `JobApplicationViewModel.ToModel`; [JobApplicationRepository.cs](../../src/ResumeBuilder.Data/ResumeBuilder.Data/JobApplicationRepository.cs#L77).

`ToModel` constructs a new entity without preserving `CreatedAt`. `AppliedOn` is read-only on the view model and never receives the date assigned by the repository. For a Saved row changed to Applied, subsequent notes edits keep submitting a null applied date. The repository then assigns a new date each time. The current row continues to say Not sent yet.

**Fix:** update the persisted entity by identity, preserving creation metadata. Return assigned dates to the view model, notify dependent properties, and assign the applied date only on the relevant status transition. Provide explicit date correction for backfilled applications.

**Acceptance:** Saved to Applied sets one date. Later text edits preserve it and `CreatedAt`, and the displayed age updates immediately.

### B06 Accepted AI edits overwrite newer manual text

**P1. Reproduced.** [JobTailoringService.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/SmartContent/JobTailoringService.cs#L177), `Apply`.

The edit carries `Original`, but Apply ignores it. A proposal based on old text overwrites a field the user has since revised. Experience targets use collection indices, so removing or reordering roles can also redirect a proposal.

**Fix:** give editable items stable identities and bind proposals to a document revision plus expected field value. Reject stale proposals or offer a fresh comparison. Construct undo actions only for edits actually applied.

**Acceptance:** editing, deleting, or moving a target after analysis cannot overwrite a different field. An unchanged target still accepts and undoes the rewrite.

### B07 Switching sync folders reuses the old deletion history

**P1. Reproduced.** [LocalFolderSyncService.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/Sync/LocalFolderSyncService.cs#L52), `ConfigureAsync` and `SyncOneAsync`; [SyncStateStore.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/Sync/SyncStateStore.cs).

Sync a resume to folder A, configure a new empty folder B, and sync again. The same state file is reused, so absence in B is interpreted as a remote deletion. The probe uploaded zero documents to B and produced a deletion warning. The App does not display `SyncResult.Warnings`.

**Fix:** scope state to a sync destination identity. Treat a newly selected destination as a new pairing unless the user explicitly adopts an existing pairing. Persist the destination, and surface warnings in the result panel.

**Acceptance:** selecting a new empty destination uploads current documents; returning to the previous destination preserves its own history. Real deletions still do not resurrect automatically.

### B08 Synced variants attach to unrelated local resumes

**P1. Reproduced.** [Resume.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/Models/Resume.cs#L29), `BaseResumeId`; [LocalFolderSyncService.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/Sync/LocalFolderSyncService.cs#L330), `SaveDownloadedAsync`.

Sync preserves `SyncId`, but transports the integer `BaseResumeId` unchanged. On another database, that integer can identify another resume. The two-database probe imported a variant whose parent became Unrelated local resume.

**Fix:** serialize the parent using a stable sync identity and resolve the local foreign identity after import. Clear foreign local identities on ordinary file import. Also prevent creating multiple local rows with one SyncId when an already-synced remote is manually imported; resolve the existing identity or explicitly duplicate it with a new one.

**Acceptance:** sync a base and variants between databases with deliberately different ID assignments. Relationships remain correct regardless of import order. A missing parent remains unlinked rather than attaching by coincidental integer ID.

### B09 Multi page PNG success actions point to a missing file

**P2. Reproduced.** [PngExporter.cs](../../src/ResumeBuilder.Export/ResumeBuilder.Export/PngExporter.cs#L87), [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs), `ExportAsync`.

The exporter writes `export-p1.png` and following pages, while the success toast stores `export.png`. The probe wrote five page files and no file at the toast path. Open and Show in folder therefore target the wrong result. The save picker also cannot warn about overwriting all derived page filenames.

**Fix:** return an export result containing the paths actually written. Open the first page and reveal the output folder, with a count of exported pages. Check overwrite decisions for the complete output set, or offer an explicit directory export.

**Acceptance:** success actions reference existing files for one and multiple pages, and collisions with existing page files follow the user's overwrite choice.

### B10 Saving a variant overwrites the base and keeps editing it

**P1. Reproduced through the App command.** [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs#L2142), `SaveAsVariantAsync`.

The command first saves the current edited resume, then duplicates that persisted row as a variant. If the user tailored the base, the base has already been overwritten. The command does not switch `CurrentResume` to the variant, so further edits keep changing the base.

**Fix:** branch a draft before applying job-specific edits. For the current command, create the variant directly from a snapshot of the editor without updating an existing base, persist it, and switch the editor to the returned variant. Define the first-save behaviour for an unsaved base explicitly.

**Acceptance:** tailor and save a variant, close and reopen both: the base keeps its original content, the variant keeps the job-specific content, and the editor's active identity is the variant.

### B11 Save success can allow navigation while edits remain unsaved

**P1 under asynchronous save timing. Reproduced with an injected repository delay.** [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs#L2579), `SaveAsync`, `ConfirmDiscardChangesAsync`, and `ApplyUpdateAsync`.

DirtyTracker correctly preserves `IsDirty` for an edit made during a save. However, SaveAsync returns true anyway. Callers use that boolean to permit document replacement or process restart. The probe returned true with `IsDirty` true and newer text absent from the database.

**Fix:** distinguish a completed write from all pending work being saved. A close, replacement, or update must wait for the current document generation to be durable, or leave the transition cancelled. Save a snapshot and reconcile the returned identity/version to the same document session. Protect sync reloads with the same document-generation check.

**Acceptance:** pause a save, edit, then resume it while closing, opening another resume, or applying an update. No transition discards the newer edit. Repeat while another document is selected during an in-flight autosave.

### B12 Autosave recreates deleted documents

**P1. Reproduced from the post-confirmation state.** [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs#L2794), `DeleteResumeAsync`; [MainWindowViewModel.CoverLetters.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.CoverLetters.cs#L382), `DeleteCoverLetterAsync`.

Deleting the open resume sets its ID to zero and marks it dirty. The next autosave creates it again. The letter deletion path has the same structure while its editor is open. The resume probe executed that state transition after a real database deletion and confirmed recreation.

**Fix:** after confirmed deletion, replace the editor with a clean blank document or close the deleted letter's editor. If retaining content is desired, make recovery an explicit action that creates a new identity. Coordinate deletion with in-flight saves.

**Acceptance:** delete the active document and advance the autosave clock. It remains deleted. A later intentional new document can save normally. Verify the equivalent cover-letter path.

### B13 AI proposals survive switching documents

**P1. Reproduced through load and apply commands.** [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs#L1008), `LoadResumeIntoEditor`, `ResetToNewResume`, and `ApplyAcceptedEdits`.

Loading another resume leaves the prior resume's proposals and analysis in the shared view model. The probe loaded a new resume and successfully applied the previous document's summary proposal to it. An in-flight AI result can also arrive after the document has changed.

**Fix:** clear document-specific analysis and suggestions when the active document changes. Cancel outstanding work and validate document identity and generation before publishing results. Scope draft and proposal state to an editor session.

**Acceptance:** generate or inject a proposal for A, open B, and attempt to apply it. B stays unchanged. Complete a delayed request for A after opening B; no result appears in B.

### B14 The remote list exposes deleted archives as active documents

**P2. Reproduced.** [LocalFolderSyncService.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/Sync/LocalFolderSyncService.cs#L517), `ListRemoteAsync`.

The sync participant reader excludes `.conflict.json` and `.deleted.json`. The remote list excludes only conflict files, so parked deletions remain available as if they were current remote resumes.

**Fix:** use one shared classifier for canonical participants, conflict archives, and deleted archives. Offer recovery separately if needed.

**Acceptance:** deleted and conflict archives are absent from the active list and cannot be accidentally reimported through it.

### B15 Shared template state changes other documents during rendering

**P1. Reproduced deterministically.** [TemplateRegistry.cs](../../src/ResumeBuilder.Templates/ResumeBuilder.Templates/TemplateRegistry.cs#L10), [BaseTemplate.cs](../../src/ResumeBuilder.Templates/ResumeBuilder.Templates/BaseTemplate.cs#L26), [BaseCoverLetterTemplate.cs](../../src/ResumeBuilder.Templates/ResumeBuilder.Templates/BaseCoverLetterTemplate.cs#L24).

The registry returns shared template instances. `CreateDocument` mutates instance fields including settings, current resume, and ordered sections; rendering reads those fields later. Create document A with a visible summary, create B with its summary hidden using the same template, then render A: A's summary disappears. Preview, export, and thumbnail rendering share the registry and can overlap. Cloning the input resume does not isolate the template instance.

**Fix:** create a fresh template renderer for each operation through factories, or make rendering stateless with an immutable render context. A lock around only CreateDocument is insufficient because generation happens later. Apply the same isolation to cover-letter settings.

**Acceptance:** prepare A and B before rendering either, then render them in both orders. Each retains its own visibility, ordering, and styling. Add overlapping preview, thumbnail, and export checks across all registered templates.

### B16 Keyword analysis counts hidden content

**P2. Reproduced.** [ResumeTextExtractor.cs](../../src/ResumeBuilder.Core/ResumeBuilder.Core/SmartContent/ResumeTextExtractor.cs#L12).

The analysis extractor reads every section regardless of visibility. Hiding a skill removes it from the exported resume but leaves it in the keyword score. The user can therefore receive a match result based on qualifications absent from the document being sent.

**Fix:** distinguish the complete profile from the visible resume text. Use the visible text for the displayed document match score. Consider a separate suggestion that relevant hidden experience is available.

**Acceptance:** hiding the only section containing a required keyword removes that match; showing it restores the match. Confirm against extracted exported PDF text.

### B17 Drafting an existing cover letter uses the unrelated current resume

**P1. Reproduced through the App command without AI.** [MainWindowViewModel.CoverLetters.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.CoverLetters.cs#L212), `DraftCoverLetterWithAiAsync`.

A stored letter can belong to a different resume from the one open behind the overlay. Drafting always reads `CurrentResume`, the current resume's target role, and the current job-description textbox. It does not resolve the letter's source or use its stored job description. The probe inserted the unrelated resume's summary into the letter.

**Fix:** resolve the letter's linked resume or saved source revision, use the letter's own target/job context, and show the source clearly. If the source was deleted, require explicit source selection. Reject late results after the letter changes and preserve manually written paragraphs until the user accepts replacement.

**Acceptance:** open resume A, then an existing letter for B. Drafting uses B and the letter's posting. A delayed draft cannot replace another letter's body.

### B18 Application save failures are silently abandoned

**P1. Source confirmed.** [MainWindowViewModel.Applications.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.Applications.cs#L135), `SaveApplicationAsync`; [ItemViewModels.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/ItemViewModels.cs), `Persist`.

Each keystroke launches a fire-and-forget update. Failures are swallowed; there is no pending state, retry queue, or close guard. If the last edit fails and the user closes or reopens the tracker, it can disappear without warning. Multiple writes also lack per-row ordering or concurrency control.

**Fix:** debounce and serialize saves per row, snapshot each generation, retain failures as pending, and expose a quiet persistent failure indicator with retry. Include pending tracker edits in close/update handling. Add a row concurrency token and preserve newer edits when a response returns.

**Acceptance:** inject a failing repository for the final edit. The change stays pending and retryable, and closing cannot silently discard it. Rapid edits remain ordered.

### B19 Global document shortcuts remain bound to the resume under the letter editor

**P2. Source confirmed; keyboard dispatch requires GUI verification.** [MainWindow.axaml](../../src/ResumeBuilder.App/ResumeBuilder.App/Views/MainWindow.axaml#L18).

Window shortcuts bind Save and Export directly to resume commands. The cover-letter overlay does not provide contextual replacements. When these global bindings execute while a letter is open, they operate on the underlying resume. Undo history is also owned by the resume rather than the active letter.

**Fix:** route document commands through the active editor, including Save, Export, Open, New, and Undo. Add platform-appropriate Command shortcuts on macOS and define overlay focus behaviour in the design.

**Acceptance:** keyboard Save and Export act on the visible document, and Undo affects its edits. Verify focus, Escape, and shortcuts on Windows and macOS.

### B20 A successful first run import leaves onboarding covering the editor

**P1 for activation. Reproduced at the App state boundary.** [MainWindowViewModel.cs](../../src/ResumeBuilder.App/ResumeBuilder.App/ViewModels/MainWindowViewModel.cs#L3091), `AdoptImportedResume`; [FirstRunOverlay.axaml](../../src/ResumeBuilder.App/ResumeBuilder.App/Views/FirstRunOverlay.axaml).

The first-run import commands populate the resume, but adoption never clears `ShowFirstRun`. The imported editor remains covered until another action clears the overlay, such as a later successful autosave reloading the saved list. The probe populated Jane while the onboarding flag remained true.

**Fix:** close onboarding after successful adoption, preserve it on cancellation or failure, and direct focus to the import review or first populated section.

**Acceptance:** import a valid file on a fresh database and see the populated editor immediately, without waiting for autosave. Cancelled and failed imports preserve the starting screen.

## Engineering and quality needs

The layered Core, Data, Templates, and Export projects are a useful foundation. Short-lived contexts, optimistic concurrency, upgrade backups with WAL handling, content-preservation tests, and three-OS CI are worth retaining. The main gap is that library tests do not verify how the App composes those behaviours.

1. **Add an App workflow test boundary.** The current test project excludes App. Extract editor-session and transition logic into testable services, or add an Avalonia headless test project. Test actual menu identifiers and command flows, not only direct exporter calls. Keep a small installed-app smoke matrix for file dialogs, focus, DPI scaling, and updates.
2. **Reduce shared state deliberately.** MainWindowViewModel and its partials coordinate resume editing, letters, applications, AI, sync, preview, and saving. Extract document sessions, an active-document command router, an application save coordinator, and an export-result service. Do this alongside defect repairs rather than as a prerequisite rewrite. Ensure undo actions survive editor refreshes instead of retaining setters to discarded item view models.
3. **Serialize writes and bound background work.** Resume saves have a gate; cover-letter saves do not share equivalent protection across manual save and timer calls. Preview cancellation suppresses stale results but cannot interrupt a QuestPDF render already executing. Limit concurrent renders and coalesce pending previews. Test delayed saves, document switching, deletion, and shutdown together.
4. **Strengthen input and recovery boundaries.** Validate imported null collections, nested objects, enum values, dates, and render settings before adoption. Bound file sizes, ZIP expansion, page counts, and image dimensions; provide cancellation. Use staged writes for exports and recover cleanly after interrupted writes. These are hardening needs, not demonstrated remote exploits.
5. **Keep designs current.** The design source covers four screens and selected components, while the app includes more overlays and states, including Applications. Extend coverage to recovery, sync conflicts and warnings, application save failures, keyboard focus, and narrow laptop layouts. The fixed 196-unit navigation column, wide command bar, and 460-unit letter editor need visual checks at 800 by 500 and common scaled laptop sizes. Clipping at those sizes was not measured in this review.
6. **Schedule the runtime upgrade now.** `Directory.Build.props` targets .NET 8 and CI installs its SDK. Microsoft ends .NET 8 support on **November 10, 2026**; .NET 10 LTS is supported through November 14, 2028. Migrate and repackage self-contained releases before that deadline. Updating the user's installed runtime alone does not replace the runtime bundled in this app. [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

Translate headings and dates centrally. Add UI localization and right-to-left support only with actual user validation. | 4 to 7 days for paper size and one extra document language |

If implemented, use supported OS credential stores without a plaintext fallback and update the privacy description.

## Business needs for adoption

### Positioning

Use a specific proposition: **Create and tailor resumes on your computer, with no account, no export paywall, and optional local AI.** Explain that cloud AI sends selected text to the configured provider and that cloud-synced folders are governed by that storage provider. The README's absolute opening claim that a resume never leaves the machine needs this qualification alongside it.

The existing roadmap's claim that competitors are all subscription services is no longer a sound basis for positioning. Reactive Resume currently advertises a free open-source builder, bring-your-own-key AI, cover letters, application tracking, and exports. FlowCV advertises a free first resume with unlimited PDF downloads. These are vendor claims, not independently tested product comparisons. [Reactive Resume](https://rxresu.me/), [FlowCV](https://flowcv.com/)

The implication is to emphasize the desktop and account-free workflow, ownership, and dependable offline use. A template-count contest is a weak acquisition strategy.

### Current signals and their limits

Read-only GitHub queries during this review returned four stars, one fork, and zero open issues. Ten releases had 1,826 downloads across all assets, but only 549 were installer, portable, or AppImage downloads. The rest include package and feed assets. The latest release was v1.2.3, published August 8, 2026: its seven installer/portable/AppImage assets totalled 279 downloads, including 244 Windows installer downloads. These counters include repeat and automated downloads; they do not establish installations, active users, or retention. [Repository](https://github.com/Gentian28/resume-builder), [release metadata](https://api.github.com/repos/Gentian28/resume-builder/releases?per_page=100)

This supports trying a Windows-led acquisition campaign while retaining cross-platform support. It does not establish that Windows users activate successfully. Use installer downloads separately from updater traffic when preparing adoption evidence, including a code-signing reapplication.

### Acquisition and installation trust

The GitHub repository has no homepage URL configured. The checked-in download-page reference still contains a placeholder screenshot instruction, and the README has no embedded product walkthrough. The reference explicitly requires porting into the portfolio, so its state does not prove what the live portfolio currently serves. Audit the actual public route and platform links before changing or promoting it.

Prepare one canonical download destination with real screenshots, a short install-to-export demonstration, prominent Windows winget instructions, all platform choices, and accurate unsigned-build guidance. Verify downloads from a clean machine. Keep code signing and macOS notarization as separate distribution jobs; the existing signing reapplication item already covers the pending owner action.

Recruit a small first cohort through people likely to value offline use: privacy-conscious job seekers, users of local models, and career advisers. Treat these as candidate segments to test. Do not start by paying for broad traffic. Offer a reproducible example resume and a concrete task instead of a feature list.

### Activation and retention

Define activation as **a user produces a PDF they would be willing to send**, rather than downloading the installer or creating a blank record. For each participant, observe installation, first import or example, first meaningful edit, template choice, export, and finding the exported file. Record task completion and obstacles with consent.

Interview five to ten people initially. Ask what brought them to the app, which file they already had, whether anything was lost on import, whether they trust the exported result, and what would make them reopen it. Run the same scripted task before and after the repair release.

For retention, observe whether people return for a second job-specific variant or to update an application. Resume software is used episodically. Daily activity is a poor success measure for this product; returning during the next application is more meaningful.

### Measurement without telemetry

Keep the no-telemetry promise. Start with public release counters, counts of support requests, and an opt-in usability cohort. Aggregate website acquisition data can be considered separately under the website's own privacy terms; do not add in-app event collection under an unrelated analytics credential.

| Measure | Collection method | Initial decision it supports |
| --- | --- | --- |
| Successful clean-machine installation by OS | Scripted tester checklist | Which installation instructions or packages need repair |
| First usable export completion and time | Consenting observed sessions | Whether onboarding and imports improve activation |
| Import field preservation | Synthetic fixtures plus participant review without retaining personal files | Whether to improve PDF parsing or prioritize DOCX import |
| Repeat use for a second application | Opt-in follow-up with cohort | Whether variants and application tracking create return value |
| Support burden per repair release | Issue labels and maintainer time | Whether to slow feature work for reliability |
| Installer asset downloads by release and OS | GitHub metadata, excluding feeds and package assets | Whether a specific promotion generates interest |

Do not assign a conversion rate using downloads as the denominator and cohort participants as the numerator. They are different populations. After the first cohort, set numeric improvement targets against the measured baseline.

### Community and sustainability

Add issue forms for bugs and feature requests, a short CONTRIBUTING guide, a security-reporting route, supported-platform requirements, and release smoke-test instructions. Give contributors small bounded tasks such as a translation fixture, importer edge case, or an accessibility fix. Keep core reliability ownership clear.

Optional donations or sponsorship can support signing and maintenance while every product feature remains free. Start with transparent costs and release quality. There is no validated need here for subscription billing, user accounts, or a hosted AI subsidy.

Before each UI change, publish a proposal beside the relevant current design and obtain approval under the project's design rules. Verified command-wiring and persistence defects should stay distinct from decisions about a new screen. After implementation, update any design that diverged and promote the approved proposal to the current card.

Each release should pass the existing suite, targeted workflow regressions, a clean-profile import-to-export check, a previous-version database upgrade with restore, and the supported installer/update smoke matrix. Validate new snapshot and relationship columns against DatabaseInitializer and its schema guard; adding a property alone does not upgrade existing installations.

Defer a web rewrite, native cloud OAuth integrations, additional template volume, account systems, and automatic cloud AI. The existing architecture preserves future options. The next product decision should follow repaired workflows and observed users.
